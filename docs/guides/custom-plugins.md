Every built-in plugin — `typescript()`, `sdk()`, `zod()`, and the rest — implements the same `ApigPlugin` interface. Your own plugin is written exactly the same way, with no special access to apig internals.

## Minimal example

```ts
import type { ApigPlugin } from "@travjek/apig";

export const myPlugin = (): ApigPlugin => ({
name: "my-plugin",
fileName: "my-output",
scope: "root",
generate(ir) {
  const lines = ir.operations.map(
    (op) => `// ${op.method} ${op.path} → ${op.id}`,
  );

  return {
    code: lines.join("\n"),
    exports: [],
    typeExports: [],
  };

},
});
```

```ts
import { defineConfig } from "@travjek/apig";
import { myPlugin } from "./my-plugin";

export default defineConfig({
input: "./openapi.json",
output: "./src/api",
plugins: [myPlugin()],
});
```

That's it — `apig generate` picks up the plugin right alongside the built-in ones and writes `my-output.ts` to the output directory.

## The ApigPlugin interface

```ts
interface ApigPlugin {
name: string;
fileName: string;
scope: 'root' | 'operations';
generate: (ir: IR, config: ApigConfig, ctx?: PluginContext) => PluginResult;
generateRootFiles?: (ir: IR, config: ApigConfig) => ExtraFile[];
withTypes?: boolean;
schemaSuffix?: string;
}
```

| Field          | What it means                                                                                                                                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`         | A unique name. apig uses it to look up the plugin in dependency checks — `mcp()` uses this same name to check whether `sdk()` is enabled alongside it.                                                                          |
| `fileName`     | The base output file name, without extension. `"sdk"` becomes `sdk.ts`, and with `groupBy: "tags"` it becomes `pet.sdk.ts`.                                                                                                     |
| `scope`        | `"root"` — the plugin runs once for the whole IR (like `typescript()`, `zod()`, `faker()`). `"operations"` — it runs again for every group under `groupBy: "tags"` or `"endpoints"` (like `sdk()`, `tanstackQuery()`, `swr()`). |
| `withTypes`    | Defaults to `true`. Set it to `false` if your plugin doesn't emit its own TypeScript types — otherwise apig won't automatically suppress `typescript()`, even if it considers your plugin a validation plugin.                  |
| `schemaSuffix` | The suffix your plugin appends to generated schema names. Only needed by validation plugins — it's how `rhf()` and `mcp()` find your schemas without forcing the user to duplicate the suffix in two places in the config.      |

## PluginResult

What `generate()` returns.

```ts
interface PluginResult {
code: string;
exports: string[];
typeExports: string[];
}
```

`code` — the entire file's contents. `exports` and `typeExports` are only needed if you have `index: true` turned on — apig uses these lists to build `index.ts` with re-exports. Empty arrays just mean the file won't show up in the combined re-export — the content itself is unaffected.

> **Don't forget the marker at the top of the file**
>
> apig cleans the output before regenerating, but it only removes files that have the string `auto-generated by @travjek/apig` in their first 200 characters — that way other people's files in the same folder stay untouched. Without this string at the start of `code`, your file just gets left alone on the next `apig generate` and turns into orphaned junk nobody cleans up.

```ts
const banner = "// auto-generated by @travjek/apig — do not edit manually";
generate(ir) {
return {
  code: [banner, "", "export const hello = 'world';"].join("\n"),
  exports: ["hello"],
  typeExports: [],
};
}
```

There's no ready-made `banner` constant exported from the `@travjek/apig` package — you write the marker string yourself, exactly once, in your own plugin.

## IR — what the plugin works with

```ts
interface IR {
operations: IROperation[];
schemas: IRSchema[];
}

interface IROperation {
id: string;
method: 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE';
path: string;
tag: string;
deprecated: boolean;
params: { path: IRProperty[]; query: IRProperty[]; header: IRProperty[] };
body: { schema: IRSchema; required: boolean; contentType?: 'json' | 'multipart' } | null;
response: IRSchema | null;
errors?: { status: number; schema: IRSchema }[];
summary?: string;
description?: string;
}
```

IR is no longer the raw OpenAPI document — it's a normalized intermediate representation: 3.0 and 3.1 already look identical by this point, `id` already accounts for `rename` from the config, and `params` are already split into path/query/header. You don't have to write your plugin against a specific spec version — that work is already done for you.

## Checking dependencies between plugins

If your plugin builds on another plugin's output — say, it wraps SDK functions — it's worth checking for it explicitly and failing with a clear message, instead of breaking on an empty import.

```ts
generate(ir, config) {
const hasSdk = (config.plugins ?? []).some((p) => p.name === 'sdk');
if (!hasSdk) throw new Error('my-plugin requires sdk plugin — add sdk() to plugins');
// ...
}
```

That's exactly what `msw()` does — it throws if `faker()` isn't in `plugins`. `mcp()` checks two dependencies at once — `sdk()` and `zod()`. An exception from `generate()` propagates up to the CLI and gets printed with a clear error message — you don't need to write your own handler for it.

## scope: "operations" and PluginContext

Plugins with `scope: "operations"` get a third argument, `ctx` — import paths you should use instead of hardcoding them, because they change depending on `groupBy`.

```ts
generate: (ir, config, ctx) => {
const sdkImport = ctx?.sdkImportPath ?? "./sdk";
const configImport = ctx?.configImportPath ?? "./config";
// ...
}
```

| ctx field               | When it changes                                                     |
| ----------------------- | ------------------------------------------------------------------- |
| `sdkImportPath`         | `./sdk` with no grouping, `./pet.sdk` under `groupBy: "tags"`       |
| `queryKeysImportPath`   | Only set when `queryKeysStyle: "object"`                            |
| `configImportPath`      | Path to the shared `config.ts` with `ApigError`                     |
| `customErrorImportPath` | Set if the config has a custom error class via `errorHandling.path` |
| `clientImportPath`      | Path to the file with the custom HTTP client instance               |

## generateRootFiles — shared files outside of groups

If your plugin needs a single file for the whole project — not one per group — use `generateRootFiles`. It's called once with the full IR, after all the groups have already been written.

```ts
generateRootFiles: (ir, config) => [
{ fileName: 'my-shared-file.ts', code: '/* ... */' },
],
```

This is how `tanstackQuery()` works with `queryKeysStyle: "object"` — instead of a key in every group file, it emits one shared `query-keys.ts` at the output root.

## What it works with

> Your own plugin sees the same IR as the built-in ones and is written the same way — there's no separate extension API. If it replaces `typescript()`, set `withTypes: true` — apig suppresses the duplicate type plugin automatically, the same way it does for `zod()`, `valibot()`, and `yup()`.
